# 问题驱动诊断向导：待机掉电与使用发热

日期：2026-10-03。代码基线：`b4bd6cd`。状态：用户已确认设计及实施计划，正在逐项实施和独立审查；本文定义目标，不表示全部功能已实现或已验证。

## 1. 目标与范围

用户要求同时设计“待机掉电排查”和“使用时发热排查”，此前强调 AI 输出应精准、有指向性。成功标准是让用户知道：目前观察到了什么、哪些解释尚未证实、还缺什么，以及下一步最值得做的一件事。输出长度或建议数量不是成功指标。

设计假设：面向普通手机用户，继续支持可选 Root 的只读诊断；无 Key 可完成核心排查；在线解释须主动确认。两场景共用证据和动作框架，使用独立规则，不把发热简单当成耗电排名问题。

第一版不做后台持续监控、自动采样提醒、自动系统调整、压力测试、健康百分比、硬件故障诊断、跨设备正常值排行榜或新的 Shizuku 连接。无需新服务商、新服务器或新权限。

## 2. 方案取舍与项目接入

采用“本地规则决定排查结果和下一步，模型只解释已批准的内容”。纯聊天追问成本低，但无法可靠约束归因；全天趋势系统可能提供更多数据，但会引入覆盖、耗电与存储问题，留到后续独立设计。

复用 `PowerDiagnosticSnapshot` 的来源、字段覆盖、应用组和窗口元数据；复用 Bug Report 导入、Root 白名单采集、基础设备快照、已有续航观察和本地验证记录。`BatteryInfo.temperatureCelsius` 是电池温度，不是 CPU 或机身表面温度；`SystemPowerEvidence.thermalStatus` 是另一类证据。

新逻辑在独立模块中接入现有入口，不整体重写 MainActivity、诊断解析器、聊天归档或云端协议。预期新增职责名称如下，实施时按现有目录习惯定位：

- `GuidedDiagnosticSession`：场景、用户回答、已确认样本和版本。
- `GuidedEvidenceAdapter`：将现有对象转换为带出处的白名单证据，不生成新的事实。
- `IdleDrainRuleSet` / `UsageHeatRuleSet`：纯 Kotlin 场景规则。
- `GuidedAssessment`：事实、候选解释、缺口、主动作及拒绝原因。
- `GuidedDiagnosticViewModel`：会话、异步任务、样本确认和过期结果保护。
- `GuidedDiagnosticScreen` / `GuidedExplanationPayload`：界面和可选解释边界。

依赖方向为“输入 → 证据适配 → 场景规则 → 界面／模型解释”；模型结果不能反向改写规则结论。

## 3. 共同交互与生命周期

入口设在 Agent 的系统耗电诊断附近，新增“按问题排查”，选择两种场景之一。不自动进入 Root 授权或自动发送在线请求。

流程：选择问题 → 回答必要问题 → 主动选取／采集证据 → 预览确认 → 本地评估 → 执行一个手动下一步 → 用户主动更新证据。每个问题均允许“不确定”，不能通过默认勾选生成肯定声明。

页面固定展示四部分：

1. 已知事实：数值或状态、来源、时间含义、证据编号。
2. 待验证解释：最多三项，分别列支持证据、反证或缺口；不输出伪精确概率。
3. 尚缺证据：按影响排序，不把“来源不支持”反复当成可重试任务。
4. 下一步：一个主动作，说明目的、前提、局限及返回后的判定条件。可以展开其他选项，但不自动执行。

会话状态为 `ANSWERING`、`NEEDS_EVIDENCE`、`READY`、`AWAITING_USER_ACTION`、`ENDED`。证据不足是正常结果，不是报错；导入失败、采集失败、在线请求失败单独表示，不清空已有有效数据。

第一版向导仅保存在页面级 ViewModel 内存中，配置变化保留，进程死亡后重新开始；页面明示这一限制。不给向导新增独立持久化归档。用户主动建立的验证记录沿用现有加密留存、删除和容量边界。

切换场景或替换证据必须确认；新报告到达只展示“有新样本可选择”，不能静默替换当前样本或继承旧样本的确认。会话、样本集合和用户回答各有版本；任何变化使旧评估及模型结果失效。异步完成时校验版本，拒绝迟到结果。

解释控制器归页面 ViewModel 所有，不归 LazyColumn 列表项所有。滚动不丢结果、不取消请求；退出当前向导、显式停止或更换输入时取消，并提示远端可能已接收请求。第一版不持久化 AI 回答。

## 4. 证据与动作契约

每条证据至少包含：本会话内稳定 ID、类型、值与单位、来源、来源状态、字段状态、实际／估算标记、应用组、采集／导入时间、报告事件时间（可未知）、统计窗口（可未知）。不同时间字段不得互相代用。用户自述作为独立类型保留，不能升级成系统观测。

保留零值、未知、不可用、截断和冲突，不以空串或零代替缺失。应用归属须同时检查 UID／包名映射完整性；共享 UID 只展示应用组，不拆分归因。不同来源或不同统计区间的数据不能直接求和或相互补齐。

候选解释使用稳定规则 ID、证据 ID 集合和缺口 ID 集合。事实只能引用存在且适用的证据；来源不完整的数值可作为带警示的原始观察，不能驱动具体应用调整。

动作来自本地白名单，类型为补充回答、导入报告、重新采集、打开已有粗略续航观察、观察一个条件变化、打开既有验证记录或结束排查。动作含稳定 ID、原因、前提、用户操作说明、停止条件和返回判据。

选择顺序：已有系统警告需要用户处理 → 输入冲突 → 关键证据缺失 → 单变量观察／验证 → 无进一步可靠动作则结束。一次只展示一个主动作；同优先级按规则固定顺序选取，保证离线结果可重复。

## 5. 场景一：待机掉电排查

### 输入与最少追问

询问问题发生的大致起止、期间是否充电、是否主要处于息屏闲置、是否跨重启。时间未知允许继续，但限制结论。只有需要缩小候选时才追问音频播放、导航、热点等持续任务；用户自述不证明系统整个区间的实际状态。

### 证据需求与分支

| 情况 | 可以说什么 | 优先下一步 |
| --- | --- | --- |
| 只有当前电量或体感掉电快 | 尚不能量化本次区间 | 用户主动使用已有粗略续航观察，或提供系统报告 |
| 两点式观察有效 | 指定区间平均掉电速度，沿用已有有效性门控 | 若用户要查应用原因，再导入系统报告 |
| 报告区间与问题区间关系未知 | 报告内累计活动，不代表本次待机 | 说明时间缺口；可重新采集，但不承诺能补出窗口 |
| 包名映射截断／共享 UID | 归属不完整或仅能归到应用组 | 禁止单应用限制建议；尝试支持的完整映射来源 |
| 存在唤醒、任务或后台活动 | 相关活动线索，不自动等同耗电原因 | 结合时段和用户任务确认，缺证据则继续观察 |
| 候选具备适用证据且现有建议规则允许 | 值得验证的解释，非已证实原因 | 一项可回退的手动调整，并建立既有验证记录 |

没有读取到某项活动不能推出“没有活动”。唤醒次数不等于唤醒时长，累计时长不等于待机区间时长，平均掉电速度不推算全天续航或电池寿命。没有可比窗口时只并列数据；沿用现有比较引擎拒绝规则。

示例输出意图：“报告记录了应用组 A 的后台活动，但统计窗口无法对应昨晚的待机区间，因此暂不能认定它造成昨晚掉电。下一步先确认报告时间范围。”示例不是硬编码诊断结论。

## 6. 场景二：使用时发热排查

### 输入与最少追问

先问“现在仍在发热还是已经结束”，再问发生时主要任务（游戏、视频、导航、充电时使用、其他）及是否充电。任务时长、外壳／环境变化只在需要单变量观察时追问，均可未知。应用名称为用户指认，不能自动等同系统归因。

### 证据需求与分支

| 情况 | 可以说什么 | 优先下一步 |
| --- | --- | --- |
| 只有触感描述 | 用户感到热，无法确定传感器温度或原因 | 若仍发生，主动刷新当前基础快照；否则保留为历史描述 |
| 只有电池温度 | 显示电池传感器读数、来源和采样时刻 | 按正在发生的场景补充充电／任务信息 |
| 系统热状态可读 | 展示已识别状态及来源，不换算成温度 | 如存在已识别系统警告，优先提示查看并遵循系统提示 |
| 温度与报告时间不对应 | 两次不同时间的观察 | 不融合为“该应用导致当前发热”，可采集同次会话证据 |
| 充电与使用同时发生 | 两个因素同时存在，贡献无法分离 | 用户自愿观察单个条件改变后的状态，不要求制造高温 |
| 任务结束后再次主动采样 | 该传感器两时刻读数和条件变化 | 仅描述变化，不判定故障、散热能力或优化因果 |
| 指标缺失、单位不明或来源冲突 | 当前无法可靠判断 | 给出具体缺口；不套用通用“正常温度”数字 |

不新增通用温度危险线、不将电池温度当成 CPU 温度、不把单次 CPU 频率称为热降频证据。未知热状态编码显示未知；复用或补充显式状态映射时必须以适用平台契约和测试确认，不用数字大小猜含义。

已发生系统警告时不建议继续游戏、跑分或复现高温。硬件异常判断、维修建议和安全温度阈值不在第一版能力范围；不提供关闭温控或其他保护机制的操作。

### 与复测功能的边界

热状态和电池温度不是现有耗电比较引擎的同类指标。第一版在向导内最多保留两份主动采样的有类型摘要，各自标注传感器类型、时间和用户声明条件；只作描述性并列，不计算“散热提升百分比”或宣布调整有效。

若同时存在合格的耗电摘要，可由用户明确选择建立现有耗电验证记录，并标明只验证耗电，不验证发热。否则不创建空的验证记录。专门的跨会话热实验归档留作独立后续设计。

## 7. AI 输出精准化

本地结果先完整可用，再提供“解释本次排查”。发送前预览；无 Key、离线、失败均不影响本地流程。仅发送当前场景、白名单证据、规则结果和主动作；不带普通聊天历史、原始报告、唯一设备标识。自由备注默认关闭，开启后重新预览；包名与时间的敏感性明确提示。载荷不超过 16 KiB UTF-8，超限阻止发送，不静默截断。

模型的任务是解释给定事实和动作，不是重新选动作或生成系统命令。建议响应结构为事实说明列表（附 evidenceIds）、候选说明列表（附 ruleIds）、缺口说明、主动作说明（附 actionId）。本地事实数值与动作正文固定由本地渲染，模型文字另标为“可选解释”。

校验必需结构、长度、合法 ID、禁止新增／替换动作和引用范围。格式错误、越界 ID 或违反本地门控时不展示该次模型解释，保留本地结果并说明原因。合法 ID 不证明文字语义正确，词法检查也不是语义保证；需离线对抗样本和另行授权的真实模型评测。

评测至少覆盖“未知仍未知”“共享 UID 不单独归因”“相关不写成因果”“当前温度不解释历史事件”“不改主动作”。格式通过率与人工核查的事实错误率分开报告，不以格式通过宣称准确。

## 8. 可靠性、隐私与前置修复

上线前关闭上一轮审查的七项问题并补回归：统计区段串值、零值丢失、映射不完整仍可信、跨控制器清空后复活、关闭保存失败无重试、UTF-16 截断破坏字符、列表项销毁导致解释丢失。向导不绕过这些问题另起一套不一致逻辑。

保存失败保留可重试意图并允许放弃未保存变更；只有持久化成功才显示“已保存／已结束”。全局清空屏障覆盖已排队但未进入存储层的旧操作。字符串限制采用不会切断 Unicode 代理对的明确长度规则，编码后另外检查字节上限。

每会话最多两份已确认摘要、每份最多二十个应用组，每条备注最多五百个 Unicode 码点；结构化证据白名单序列化后每份上限 48 KiB。摘要超限明确拒绝，不丢掉支持主动作所必需的证据。原始导入内容沿用现有释放策略，不为向导增加长期保留或日志输出。

“重新开始”清除会话证据、回答、结果及请求；清空聊天不删除已保存验证记录，删除验证记录不伪称已删除仍在打开的向导样本。两者界面明确区分。界面、错误与规则文案提供中英文。

## 9. 验收与测试矩阵

- 规则单测：两场景分别覆盖充分、缺失、冲突、截断、零值、未知时间、旧报告、共享 UID、跨重启及充电不明；每个结果校验事实引用、拒绝理由和唯一主动作。
- 解析回归：多统计区段、actual=0/computed>0、不完整映射；必须经过真实解析到评估的链路，不能只构造理想摘要。
- 生命周期：旋转、滚动、后台返回、退出重进、切换场景、导入迟到、取消迟到；旧请求不能覆盖新会话。进程死亡后不显示已经恢复了未持久化的样本。
- 存储：暂时失败恢复后重试、跨控制器清空、长中英文与 emoji；使用现有验证记录时继承其删除、过期和容量测试。
- 无 Key 流程：两场景均能从入口到一个解释清楚的下一步，或明确结束为证据不足。
- 发热边界：电池／CPU／表面温度不混淆，导入时间不冒充事件时间，不读取到热状态时不声称无热限制。
- AI：两种现有协议的结构契约、载荷上限、备注默认关闭、ID 越界、诱导确定归因／新增操作和网络取消；不得只依赖提示词测试。
- UI：小屏、大字体、长来源说明、键盘、读屏语义、中英文；Compose 测试编译不等于设备运行通过。

人工可用性验收：分别给用户一份缺失证据和一份存在冲突的样本，检查其能否说清“还不能确定什么”和“下一步是什么”。真实 OEM、设备生命周期及模型表现的结果独立记录，未运行必须标注，不能由 JVM 通过替代。

## 10. 建议交付顺序

先修复已确认审查问题 → 共用证据／规则／会话框架 → 待机掉电完整本地流程 → 发热完整本地流程 → 两场景可选 AI 解释 → 设备和用户验收。每阶段独立实施和审查，避免两套 UI 或推理规则相互复制。
