# Bug Report / Root 本地耗电证据归因与 AI 解释设计

## 目标

让 APA 接受普通用户主动导入的完整系统 Bug Report，也接受 Root 设备上的一键只读采集；两种入口在本地转换为同一种应用耗电证据，再由云端 AI 把本地结论翻译为普通用户能执行的说明。即使模型能力一般，用户也必须先看到明确的本地结论、证据、风险和下一步，而不是只有“可能”“证据不足”等空泛回答。

第一阶段同时完成 Bug Report 文件导入和现有 Root 采集的统一归因。系统设置中的简单耗电截图不作为主要输入；自动执行 Scene 策略、云端训练和跨用户自动数据收集不在本阶段范围内。

## 当前问题与根因

当前 Root 采集器会读取 `batterystats`、`alarm`、`jobscheduler`、`power`、`deviceidle`、`thermalservice`、`wakeup_sources` 和 UID/包名映射，但解析器主要只消费 `batterystats` 的 UID 估算 mAh，以及少量系统状态。

数据模型虽然预留唤醒锁、唤醒次数、Alarm 和 Job 字段，解析器却没有填充它们。因此每个应用通常只有一类证据，现有规则只能给低置信度“观察”建议。报告构建器再把这个弱结论交给 AI，模型没有能力恢复已经在上游丢失的信息。

根因不在 Root 权限，也不主要在提示词，而在“原始输出到结构化证据”的解析和归因缺口。

## 用户结果

用户采集一次系统耗电诊断后，应先看到 APA 本地生成的结果：

1. 总耗电最高的应用或 UID，以及统计时长和原始 mAh。
2. 后台异常第一嫌疑；如果无法判断，明确缺少哪一类证据。
3. 支持判断的独立证据，例如唤醒锁时长、唤醒 Alarm、后台 Job。
4. 一项手动 Scene 建议、可能副作用、回退方式和复测时长。
5. 每个数据源的采集与解析状态，避免把“命令执行成功”误写成“证据已解析”。
6. AI 解释单独显示在本地结论之后，不覆盖或提高本地建议等级。
7. 明确标记数据来自“用户导入的 Bug Report”还是“Root 即时采集”，但归因规则保持一致。

“总耗电最高”与“后台异常”必须分开。前台长时间使用导致的高 mAh 不能自动解释为后台异常；缺少前后台证据时必须保留这个区别。

## 方案选择

### 采用：本地证据引擎 + AI 解释

导入文件或 Root 原始输出只在读取和解析期间存在。输入适配层提取白名单系统段落，解析器把已确认字段转换为结构化证据，本地规则引擎生成稳定结论，报告构建器再向模型发送脱敏摘要。

优点是结论可测试、模型无关、隐私边界清楚，也能在以后复用给普通用户导入的 Bug Report。

### 不采用：继续只增强提示词

提示词不能恢复上游没有解析的数据。它可能让模型语气更确定，却增加误判风险。

### 不采用：把完整 Root 日志发送给模型

完整日志体积大、格式不稳定，并可能包含包名、账号痕迹、通知和系统路径。直接上传会增加隐私、费用、截断和幻觉风险。

## 架构与数据流

```text
用户选择/分享完整 Bug Report ─┐
                              ├─→ 输入适配层
Root 白名单命令 ──────────────┘
    ↓
白名单 RawDiagnosticSection
    ↓
原始输出（内存中，有限大小）
    ↓
来源专用解析器
    ↓
统一 AppPowerEvidence + EvidenceCoverage
    ↓
本地归因引擎
    ↓
LocalPowerVerdict
    ├── 直接显示给用户
    └── 脱敏结构化摘要 → AI 解释
```

### 输入适配层

两种入口只负责生成统一的 `RawDiagnosticSection`，不在入口中实现归因规则：

- `BugReportImporter`：通过系统文件选择器或分享 Intent 接收用户主动选择的 `.zip`、`.txt` 或厂商导出文件，不申请整个存储空间权限。
- `BugReportSectionExtractor`：以流式方式读取压缩包，不把条目解压到文件系统；只寻找总体大小和单条目大小均受限的文本，并提取 `batterystats`、`alarm`、`jobscheduler`、`power`、`deviceidle`、`thermalservice` 与包名/UID 映射段落。
- `RootDiagnosticAdapter`：把现有白名单 Root 命令结果映射到相同的段落名称和状态。

安全边界：

- 拒绝加密、损坏、嵌套过深或超过大小限制的压缩包；
- 不信任文件名和压缩条目路径，不进行路径落盘，避免目录穿越；
- 未识别文件只报告格式不支持，不把任意二进制内容发送给模型；
- 用户取消选择、读取中断或 Activity 重建时停止读取，不保留临时原始报告；
- 只有结构化脱敏摘要能进入云端请求，原始报告始终不能进入对话历史。

### 来源专用解析器

不继续把所有格式堆进单个 `PowerDiagnosticParser`。拆分为边界明确的纯 Kotlin 解析器：

- `BatteryStatsEvidenceParser`：统计时长、UID 估算 mAh、UID 唤醒锁及可确认的后台活动字段。
- `AlarmEvidenceParser`：按 UID/包名提取可确认的唤醒 Alarm 计数；不能确认时间窗时保留原始计数并降低可比较性。
- `JobSchedulerEvidenceParser`：按 UID/包名提取执行或调度计数，只使用格式中语义明确的字段。
- `PackageUidResolver`：合并 UID、包名和应用显示名，并显式标记共享 UID。
- 现有 power、idle、thermal 和内核唤醒源继续作为系统级上下文，不强行归属给某个应用。

每个解析器只接受文本并返回结构化结果和解析状态，不依赖 Android、Root、网络或 Compose。未知 OEM 格式返回“不支持/未解析”，不得填零。

### 统一证据

每个应用或 UID 至少包含：

- UID、包名、显示名和共享 UID 标记；
- 系统估算耗电 mAh；
- 唤醒锁总时长；
- 唤醒 Alarm 计数；
- 后台 Job 计数；
- 各字段的来源、时间窗和解析状态；
- 可选的当天前台使用时长，只作为解释上下文。

新增 `EvidenceCoverage`，分别记录“命令是否成功”和“目标字段是否解析”。报告必须能显示类似“8 个来源采集成功，3 类应用证据可用于归因”。

### 本地归因

本地归因输出两条独立排行：

- 消耗排行：依据同一统计窗口内的系统估算 mAh 排序，只称为“耗电最高”，不自动称为异常。
- 后台嫌疑排行：依据唤醒锁、唤醒 Alarm 和 Job 等后台证据归一化后排序。

规则遵循以下约束：

- 能得到时间窗时使用每小时频率，不再只看固定绝对阈值。
- 不同来源时间窗不兼容时不得直接相加，置信度必须下降。
- 一类证据只能说明线索；两类独立证据才能建议限制；高风险冻结候选仍需更严格条件。
- 前台使用时长高时，高 mAh 优先解释为使用成本，而非后台异常。
- 系统、电话、短信、桌面、支付、Root 管理器和共享 UID 不成为自动冻结候选。
- 第一版仍然只给建议，不执行冻结、限频、强停或系统设置修改。

### 本地结论与 AI 边界

新增 `LocalPowerVerdict`，内容包括：

- 本地结论类型：可归因、仅有消耗排行、证据不足；
- 第一嫌疑和最多三项排行；
- 每项的原始数值、来源、置信度和限制；
- 本地允许的最高建议等级；
- 一项 Scene 手动操作、风险、回退和复测条件；
- 证据不足时唯一最有价值的下一步。

界面先渲染“APA 本地结论”，再渲染“AI 解释”。发给 AI 的摘要使用稳定字段顺序，并明确禁止模型：

- 改写原始数值；
- 将“耗电最高”升级为“后台异常”；
- 将观察或限制升级为冻结；
- 声称已经执行 Scene 操作；
- 重复罗列无关的缺失报告。

AI 服务失败时，本地结论仍然完整可用。

## 数据与隐私

本阶段不需要训练数据库，也不需要爬取极客湾、小白测评或其他媒体的整机续航榜单。媒体测试缺少每 UID 的系统证据，不能用于验证应用归因；未经授权复制完整内容也没有必要。

首批兼容性数据来自用户可以接触到的小米、iQOO 和 vivo 三台设备。每台设备提供用户主动生成的完整系统报告；如果该机已 Root，可额外在同一时刻运行 Root 采集，用于验证两种入口是否产生一致的结构化证据。

开发所需的是少量有代表性的脱敏系统输出样本：

- 小米 / HyperOS 的 Bug Report 段落与 Root 对照样本；
- iQOO / OriginOS 的 Bug Report 样本；
- vivo / OriginOS 的 Bug Report 样本；
- 每份报告中的 `batterystats`、`alarm`、`jobscheduler` 和 UID/包名映射；
- Android 与厂商系统版本、采样持续时间和当时是否主要前台使用某应用；
- 至少一组正常前台高耗电样本和一组熄屏后台活跃样本。

原始报告仅由用户在手机上主动选择，并只在当前读取过程中使用。需要作为开发样本保留的副本只能存放在本机 Git 忽略目录。提交仓库的测试夹具必须去除账号、通知内容、路径、设备标识和无关包名，只保留解析所需的最小片段。

## 错误处理

- 用户取消文件选择不显示失败；文件损坏、加密、超限或格式不支持时给出具体原因和下一步。
- Root 拒绝、超时和来源不支持继续沿用部分成功策略。
- 命令成功但目标字段未解析时标记“格式未适配”，不能显示为零或可用证据。
- 没有兼容时间窗时仍可显示原始事实，但不计算每小时频率。
- 包名映射失败时以 UID 显示，并禁止给出冻结候选。
- AI 返回空内容、HTTP 错误或与本地等级冲突时，本地结论保持可见；模型文本不作为执行依据。

## 测试与验收

### 自动测试

- Bug Report 导入覆盖纯文本、ZIP、未知文件、压缩炸弹边界、恶意条目路径、取消和读取中断。
- 同一脱敏证据分别经文件入口和 Root 入口后，产生等价的 `RawDiagnosticSection`。
- 每个来源解析器使用最小脱敏夹具覆盖标准 Android、当前 HyperOS、截断、缺字段和格式变化。
- 归因引擎覆盖正常前台高耗电、后台多证据异常、共享 UID、关键应用、时间窗不兼容和无证据场景。
- 报告测试保证本地结论包含原始数值、来源、风险、回退和唯一下一步。
- 云端提示测试保证只发送结构化摘要，不发送原始 Root 输出，且 AI 不能获得高于本地结论的建议等级。
- UI 测试保证本地结论先于 AI 解释显示，模型失败时本地结论仍存在。

### 真机验收

在小米、iQOO 和 vivo 三台设备上分别验证报告可以被用户选择、在本地读取，并正确识别系统段落。Root 小米设备额外验证 Root 入口与文件入口的一致性。

至少完成两组受控归因测试：

1. 前台连续使用一个高负载应用后采集，APA 能将其称为“耗电最高”，但不误判为后台异常。
2. 熄屏静置后采集，APA 能引用后台证据指出第一嫌疑，给出一项可回退的 Scene 建议。

验收时记录输入来源、数据源覆盖率、第一嫌疑、置信度、建议和复测结果。没有实际真机证据时，不声称对应系统版本已完全支持。

## 实施顺序

1. 建立安全的 Bug Report 文件入口、段落提取器和输入适配接口。
2. 将现有 Root 采集接入相同的 `RawDiagnosticSection` 接口。
3. 使用小米、iQOO、vivo 的脱敏片段建立来源解析测试夹具。
4. 扩充统一证据和覆盖率模型。
5. 实现消耗排行与后台嫌疑归因。
6. 生成 `LocalPowerVerdict` 和可独立使用的本地报告。
7. 将结构化本地结论接入 AI 提示和界面。
8. 完成三机导入验收及 Root 小米双入口对照测试。
